# Система обнаружения присутствия постороннего человека за рабочим компьютером

Командный учебный проект по предмету «Реализация проекта в области информационной безопасности с использованием технологий компьютерного зрения».

Цель — разработать приложение на Python, которое использует веб-камеру для контроля присутствия людей у рабочего компьютера. В дальнейшем система должна различать владельца рабочего места и постороннего человека, фиксировать события и отправлять уведомления.

**Текущий этап — MVP с YOLO:** получение видео, обнаружение класса `person`, временное подтверждение и отображение результатов. Определение владельца и постороннего человека пока не реализовано. Версия проекта: **0.1.0**.

## Возможности текущей версии

- Захват видеопотока с веб-камеры через OpenCV.
- Обнаружение только класса `person` с помощью лёгкой предобученной YOLO11n.
- Окно с видео, рамками, `confidence` у каждого человека, `People: N` и FPS.
- Защита от одиночных ложных срабатываний: состояния `candidate → confirmed → lost`, IoU-сопоставление рамок и удержание подтверждённого человека при коротком пропуске.
- Для confidence ниже `--pose-threshold` выполняется выборочная проверка лёгкой YOLO11n-pose по keypoints. Проверки ограничены бюджетом кадра и кэшируются.
- `People: N` считает только `confirmed`. Флаг `--debug-detections` показывает кандидатов, состояние, confidence и причины решений.
- Выбор детектора, камеры, разрешения и порогов через командную строку.
- Резервный HOG-детектор OpenCV через `--detector hog`, без весов YOLO.
- На Windows: явное открытие через DirectShow (`CAP_DSHOW`), затем попытка Media Foundation (`CAP_MSMF`), если камера не открылась или не дала первый кадр.
- Ограничение времени открытия и чтения кадров, сообщения об этапах и причинах ошибок в терминале.
- Диагностика индексов камер для каждого backend без окна видео и загрузки детекторов.
- Освобождение камеры и закрытие окон при завершении работы.
- Тесты, которые запускаются без реальной веб-камеры.

Кадры обрабатываются локально в памяти. Приложение не записывает видео или фотографии и не отправляет кадры по сети. Интернет нужен для установки зависимостей и первой загрузки весов YOLO; последующие запуски используют локальный файл модели.

## Основной детектор: YOLO11n

По умолчанию используется **YOLO11n** (`models/yolo11n.pt`) — nano-вариант с 2,6 млн параметров. Для обычного ПК выбран CPU и размер обработки `320`. Характеристики модели приведены в [официальной документации Ultralytics](https://docs.ultralytics.com/models/yolo11/); фактический FPS зависит от процессора, освещения и параметров обработки и измеряется приложением, а не берётся из чужих тестов.

Модель загружается один раз перед открытием камеры. При первом запуске Ultralytics автоматически скачает веса, если их ещё нет; в терминале будет сообщение о загрузке. Веса находятся в `models/`, служебные настройки — в `.cache/ultralytics/`; эти папки исключены из Git. Для запуска без интернета заранее скопируйте веса в `models/yolo11n.pt` или укажите существующий `.pt` через `--model`.

Адаптер выбирает класс с именем `person` из метаданных модели (у стандартных весов это класс `0`) и передаёт фильтр `classes` в YOLO. Результаты дополнительно проверяются перед возвращением в приложение. Рамки относятся к исходному кадру камеры, даже если YOLO обрабатывает его в другом размере. Формат результатов описан в [документации предсказания YOLO](https://docs.ultralytics.com/modes/predict/).

YOLO подходит для более разнообразных поз и частично видимых людей, чем начальный HOG. Однако изображение только лица или маленького фрагмента головы всё ещё может не распознаться как `person`: это детектор людей, а отдельное распознавание лица пока не реализовано. При пропусках попробуйте `--imgsz 640` и `--confidence 0.2`. Более крупный вход требует больше вычислений; понижение порога увеличивает риск ложных срабатываний. Для более быстрого запуска оставьте `--imgsz 320 --device cpu`.

`confidence` показывает оценку обнаружения объекта моделью, а не уверенность в личности человека. Программа не определяет, владелец это или посторонний. HOG выбирается явно через `--detector hog`; при ошибке загрузки YOLO приложение объясняет причину и предлагает эту команду.

## Подтверждение и фильтрация ложных срабатываний

YOLO остаётся основным детектором. Его обнаружения не считаются людьми сразу: по умолчанию нужна последовательность из четырёх кадров (`--confirm-frames 4`). Рамки сопоставляются между кадрами по IoU (`--match-iou`), поэтому небольшое движение сохраняет один track. Подтверждённая рамка остаётся на экране при кратком пропуске и переходит в `lost` после `--lost-timeout` секунд; кандидат после пропуска начинает подтверждение заново.

Обнаружение со score ниже `--pose-threshold` (по умолчанию `0.7`) проходит pose-проверку. Модель `models/yolo11n-pose.pt` ищет согласованные COCO keypoints головы/лица, плеч и торса; ноги не обязательны, что сохраняет крупные планы. Высокоуверенные обнаружения не запускают pose. Результат pose для конкретного track кэшируется на ограниченное время и число кадров, а `--pose-max-per-frame` ограничивает число новых проверок за кадр. При отсутствии pose-модели сомнительный объект отклоняется.

Для диагностики сцены:

```powershell
.\.venv\Scripts\python.exe main.py --debug-detections --detector yolo --camera-index 0
```

Порог confidence остаётся только первым фильтром YOLO: его повышение одновременно может убрать настоящего человека. Поэтому временная последовательность и pose-проверка применяются независимо. Это вероятностный фильтр, а не гарантия отсутствия ложных срабатываний; качество следует проверить на собственных сценах, включая стул под тканью, крупный план лица и перекрытия.

## Ограничения HOG

HOG — начальный детектор для проверки работы приложения. Стандартная модель рассчитана прежде всего на людей, видимых в полный рост. Сидящий человек, лицо или торс крупным планом, частичные перекрытия и плохое освещение могут приводить к пропускам. Возможны и ложные обнаружения.

Минимальное окно стандартной модели имеет ширину 64 и высоту 128 пикселей. Нулевое число рамок **не доказывает отсутствие человека**. Этот MVP ещё не является готовой системой контроля доступа. Особенности модели описаны в [документации OpenCV](https://docs.opencv.org/4.x/d5/d33/structcv_1_1HOGDescriptor.html) и [официальном примере обнаружения людей](https://github.com/opencv/opencv/blob/4.x/samples/python/peopledetect.py).

Показатель `score` у HOG — оценка классификатора SVM, а не вероятность. Он может выходить за диапазон от 0 до 1. Повышение порога отбрасывает больше обнаружений; понижение может увеличить число ложных срабатываний.


Поток данных: **камера → BGR-кадр → детектор → обнаружения → окно с результатом**.

`Camera` из `camera.py` отвечает только за видеопоток. Каждый backend открывается в отдельном дочернем процессе: это позволяет завершить зависший нативный вызов OpenCV по таймауту. Снаружи остаётся простой интерфейс `with Camera(...) as camera` и `camera.read() -> BGR-кадр`. `diagnostics.py` использует этот же модуль и проверяет получение кадра для каждой пары индекс/backend.

`PersonDetector` из `detection.py` задаёт общий интерфейс `detect(frame) -> list[Detection]`; его реализуют `YOLOPersonDetector` и `HOGPersonDetector`. Затем `PersonTracker` сопоставляет результаты и выдаёт снимки `TrackedDetection` с состояниями `candidate`, `confirmed` или `lost`. Каждый результат детектора содержит:

- `Detection.box` — `(x, y, width, height)`: левый верхний угол, ширина и высота рамки в пикселях исходного BGR-кадра;
- `Detection.score` — confidence YOLO от 0 до 1 либо оценка SVM у HOG.

Детектор не открывает камеру и не рисует рамки. `main.py` создаёт выбранный детектор, tracker и (для YOLO) ленивый pose-validator, связывает компоненты и отображает результат. Ultralytics и PyTorch импортируются только при создании YOLO/pose: диагностика, HOG и дочерние процессы камеры не загружают нейросеть.

`.gitignore` исключает виртуальное окружение, кэши, веса моделей и служебные данные. `requirements.txt` содержит OpenCV, NumPy, Ultralytics, PyTorch, Torchvision и pytest.

## Требования

- Рекомендуется **64-битный Python 3.12**; код использует возможности Python 3.10 и новее.
- Веб-камера и разрешение операционной системы на её использование.
- Локальная графическая среда для окна OpenCV.
- Git для клонирования репозитория и интернет для установки зависимостей и первой загрузки модели.
- Видеокарта не обязательна: стандартный запуск использует CPU. Установка PyTorch требует заметно больше места и времени, чем исходный MVP только с OpenCV.

## Установка

MVP сейчас развивается в ветке `codex/-mvp`; ветка `main` содержит только начальный README. Клонируйте ветку MVP в папку с понятным именем:

```bash
git clone --branch codex/-mvp https://github.com/f1yxil/-.git workplace-guard
cd workplace-guard
```

Если проект уже открыт локально, повторно клонировать его не нужно. Выполняйте следующие команды из папки, где находятся `main.py` и `requirements.txt`.

Если `.venv` уже создана, обновите зависимости и запустите YOLO:

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe main.py --detector yolo --camera-index 0 --camera-backend auto --device cpu --imgsz 320 --confidence 0.3
```

## Запуск и параметры

При обычном запуске выбраны YOLO11n, CPU, вход YOLO `320`, confidence `0.3`, камера `0` и разрешение камеры `640 × 480`. На Windows режим `auto` сначала использует `cv2.CAP_DSHOW`; при ошибке или таймауте открытия/первого кадра освобождает неудачную попытку и пробует `cv2.CAP_MSMF`. На других ОС `auto` оставляет выбор backend за OpenCV.

| Параметр | По умолчанию | Назначение |
| --- | --- | --- |
| `--detector` | `yolo` | `yolo` или резервный `hog` |
| `--model` | `models/yolo11n.pt` | Путь к предобученным весам обнаружения YOLO в формате `.pt` |
| `--confidence` | `0.3` | Порог confidence YOLO от 0 до 1; на HOG не влияет |
| `--imgsz` | `320` | Размер обработки YOLO, положительное число, кратное 32; `640` для большей детализации |
| `--device` | `cpu` | Устройство YOLO; `0` для первой CUDA-видеокарты при наличии совместимого PyTorch |
| `--camera-index` | `0` | Индекс камеры; при нескольких устройствах попробуйте `1` |
| `--camera-backend` | `auto` | `auto`, `dshow` или `msmf`; явный backend проверяется без fallback |
| `--open-timeout` | `5` | Положительное конечное число секунд на одну попытку открытия, настройки и получения первого кадра |
| `--read-timeout` | `3` | Положительное конечное число секунд на получение очередного кадра |
| `--diagnose-cameras` | выключен | Проверить камеры и завершить работу без запуска детектора и окна |
| `--max-camera-index` | `4` | Для диагностики: последний индекс включительно, проверяются `0..N` |
| `--width` | `640` | Запрашиваемая ширина кадра в пикселях |
| `--height` | `480` | Запрашиваемая высота кадра в пикселях |
| `--hog-threshold` | `0.5` | Минимальная оценка SVM только для `--detector hog`; любое конечное число |
| `--confirm-frames` | `4` | Сколько последовательных кадров нужно для `confirmed` |
| `--lost-timeout` | `0.6` | Секунды удержания подтверждённой рамки при пропуске |
| `--match-iou` | `0.3` | Минимальное IoU для сопоставления рамок |
| `--pose-threshold` | `0.7` | Ниже этого confidence запускается keypoint-проверка |
| `--pose-model` | `models/yolo11n-pose.pt` | Лёгкая pose-модель для сомнительных кандидатов |
| `--pose-recheck-frames` | `8` | Интервал повторной проверки pose в кадрах |
| `--pose-cache-seconds` | `0.6` | Максимальный возраст кэшированного результата pose |
| `--pose-max-per-frame` | `2` | Бюджет новых pose-проверок на кадр |
| `--debug-detections` | выключен | Показывать candidate/lost и причины решений |
| `--config` | — | JSON-файл; значения CLI имеют приоритет |
| `--self-test` | выключен | CPU-проверка обеих локальных моделей без камеры |
| `--help` | — | Справка по запуску |

Камера может не поддерживать запрошенное разрешение и вернуть кадры другого размера. `--width` и `--height` управляют камерой, а `--imgsz` — обработкой в YOLO. Для выбора другой модели нужны веса обнаружения с классом `person`; веса классификации и модели без этого класса отклоняются.

Примеры для Windows PowerShell:

```powershell
.\.venv\Scripts\python.exe main.py --help
.\.venv\Scripts\python.exe main.py --camera-index 0 --open-timeout 5 --read-timeout 3
.\.venv\Scripts\python.exe main.py --camera-index 0 --camera-backend dshow
.\.venv\Scripts\python.exe main.py --detector yolo --imgsz 640 --confidence 0.2
.\.venv\Scripts\python.exe main.py --detector hog --hog-threshold 0.8
```

В Linux/macOS используйте те же параметры с `./.venv/bin/python main.py`.

Для завершения нажмите **q** или **Esc** в активном окне видео, закройте окно крестиком либо нажмите **Ctrl+C** в терминале.

В терминале выводятся время, уровень сообщения, индекс, backend и этап открытия. Таймаут применяется **к каждой попытке backend**, поэтому в Windows автоматическое открытие может занять до двух `--open-timeout` плюс короткое ограниченное время на завершение процессов. При зависании очередного чтения приложение завершает работу с понятной ошибкой после `--read-timeout` и очистки процесса. Переключение backend выполняется при запуске, а не посреди видеопотока.

Захват вынесен в отдельный процесс, потому что таймаут ожидания обычного Python-потока не останавливает зависший вызов драйвера. Свойства OpenCV `CAP_PROP_OPEN_TIMEOUT_MSEC` и `CAP_PROP_READ_TIMEOUT_MSEC` предназначены для FFmpeg/GStreamer и не обеспечивают такой защиты для DSHOW/MSMF; см. [документацию параметров VideoCapture](https://docs.opencv.org/4.x/d4/d15/group__videoio__flags__base.html). При превышении срока процесс захвата принудительно завершается. Никаких бесконечных ожиданий открытия, чтения или завершения процесса в приложении нет.

### Диагностика камеры на Windows

**Перед запуском закройте стандартное приложение Windows «Камера»**, видеозвонки и другие программы, которые могут занимать устройство. Если оно работает в приложении «Камера», это ещё не подтверждает доступность того же устройства через OpenCV.

Проверить индексы `0`, `1` и `2` с обоими Windows-backend:

```powershell
.\.venv\Scripts\python.exe main.py --diagnose-cameras --max-camera-index 2 --open-timeout 5
```

Диагностика последовательно проверяет **каждый индекс с DSHOW и с MSMF**, даже если первый backend уже дал кадр. Она не загружает YOLO или HOG, не скачивает веса, не открывает окна и не сохраняет кадры. Для каждой пары выводится «ДОСТУПНА» с фактическим размером полученного кадра либо «НЕДОСТУПНА» с причиной, включая таймаут. В конце выводится сводка и готовая команда с первой работающей парой индекс/backend. Успехом считается получение непустого кадра, а не только `isOpened()`.

Это проверка доступности выбранного диапазона, **не аппаратное перечисление камер**: индексы могут различаться между backend, а одно физическое устройство может быть доступно через оба. `--camera-index` на диапазон диагностики не влияет. Чтобы проверить только один backend, добавьте, например, `--camera-backend dshow`. Для трёх индексов и двух backend выполняются шесть попыток; каждая ограничена `--open-timeout`, с дополнительным ограниченным временем на завершение процесса.

Если ни одна камера не дала кадр, программа возвращает код `1`; если хотя бы одна доступна — `0`. **Ctrl+C** прерывает диагностику и освобождает камеру. Для устройств с медленным запуском можно повторить проверку с `--open-timeout 10`.

Обычный запуск с автоматическим выбором DSHOW → MSMF:

```powershell
.\.venv\Scripts\python.exe main.py --camera-index 0 --open-timeout 5 --read-timeout 3
```

Если камера не открывается, проверьте подключение и разрешение на доступ к камере **для классических приложений** в настройках конфиденциальности Windows. Сообщение `Camera index out of range` для индекса, которому не соответствует устройство, ожидаемо: используйте индекс и backend из успешного результата диагностики.

Если окно работает, но рамки не появляются, убедитесь, что выбран `--detector yolo`, проверьте освещение и попробуйте `--imgsz 640 --confidence 0.2`. При тестировании HOG человек должен быть виден преимущественно в полный рост.

## Windows-сборка и GitHub Releases

Для пользователя подготовлена production-сборка PyInstaller в режиме `onedir`: в неё входят `WorkplaceGuard.exe`, OpenCV, Ultralytics/PyTorch, конфигурация и обе локальные модели. Распространять нужно весь каталог `dist/WorkplaceGuard`, а не один exe-файл: рядом с ним находится `_internal` с библиотеками.

Разработчик собирает приложение из PowerShell одной командой. Скрипт использует `.venv`, при необходимости устанавливает зависимости сборки, проверяет CPU-инференс обеих моделей и создаёт `build/models-manifest.json`:

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\build.ps1
```

Для полностью офлайн-подготовки заранее положите `models/yolo11n.pt` и `models/yolo11n-pose.pt`, затем используйте `-SkipModelDownload`. Если зависимости уже установлены, можно ускорить повторную сборку:

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\build.ps1 -SkipDependencies -SkipModelDownload
```

Проверка собранного приложения без камеры:

```powershell
.\dist\WorkplaceGuard\WorkplaceGuard.exe --self-test
.\dist\WorkplaceGuard\WorkplaceGuard.exe --diagnose-cameras --max-camera-index 4 --open-timeout 5
```

Установщик Inno Setup находится в `installer/WorkplaceGuard.iss`. После установки Inno Setup 6.3+ соберите его так:

```powershell
& "$env:ProgramFiles(x86)\Inno Setup 6\ISCC.exe" .\installer\WorkplaceGuard.iss
```

Либо передайте `-Installer` скрипту сборки:

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\build.ps1 -SkipDependencies -SkipModelDownload -Installer
```

Итоговый файл будет создан как `dist/installer/WorkplaceGuard-Setup-v0.1.0.exe`. Установщик ставит программу в `Program Files`, создаёт пункт меню Пуск и предлагает ярлык на рабочем столе. Запуск приложения после установки выключен по умолчанию и включается пользователем на последнем шаге. Если Inno Setup не установлен, скрипт всё равно собирает приложение и сообщает, что нужно установить Inno Setup и повторить только компиляцию `.iss`.

Для GitHub Releases приложите `WorkplaceGuard-Setup-v0.1.0.exe`. Если установщик ещё не собран, допустим запасной архив всего каталога `dist/WorkplaceGuard` (включая `_internal`), но не отдельный `WorkplaceGuard.exe`. Публикация Release и отправка изменений в GitHub выполняются вручную владельцем проекта.

Пути приложения отделены от путей данных: упакованные модели и `config/defaults.json` читаются из каталога ресурсов, изменяемый конфиг хранится в `%LOCALAPPDATA%\WorkplaceGuard\config.json`. В исходниках для тестов можно задать `WORKPLACE_GUARD_HOME`. Это позволяет устанавливать приложение в `Program Files` без попытки записи туда.

## Тесты

Тесты подменяют камеру, окна и YOLO-модель: для них не нужны веб-камера, интернет и скачанные веса. Проверяются фильтрация `person`, порог confidence, рамки исходного кадра, ошибки загрузки, выбор детектора, подписи в окне и сохранение работы камеры с таймаутами. Зависимость pytest уже включена в `requirements.txt`.

Windows PowerShell:

```powershell
.\.venv\Scripts\python.exe -m pytest
```

Linux/macOS:

```bash
./.venv/bin/python -m pytest
```

Эти проверки подтверждают поведение программных компонентов. Качество обнаружения необходимо отдельно оценивать на реальных сценах рабочего места.
